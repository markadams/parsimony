# Grid's fine-grid Dslash on A100: what the hardware counters show

Mark Adams, LBNL · 2026-10-06 · Perlmutter, 1 node, 4x A100-SXM4-40GB

**Summary.** At Grid's production per-GPU volume, one fp64 domain-wall Dslash takes
1.17 ms. 62% of it is one kernel, the interior Dslash. That kernel is limited by memory
latency, not bandwidth: it reaches 59% of DRAM peak because 104 registers per thread allow
only 25% occupancy. Its register use is real; capping registers makes it spill and run up to
2x slower. Launching the interior kernel before the halo gathers, on a second stream, saves
6.6%, and with the Nc=3 unrolled kernel 11.5%. fp32 runs 2.33x faster than fp64, more than
bandwidth alone allows. These numbers are A100 only; MI250X needs the same counters
(rocprof-compute).

## Setup

- Grid `develop` `3232b438` (2026-10-05) plus three patches (below). CUDA 13.2, sm_80,
  NVTX tracing.
- `Benchmark_dwf --grid 16.8.24.48 --mpi 1.1.2.2 -Ls 24 --accelerator-threads 8 --comms-overlap`.
  That gives 16x8x12x24 x Ls 24 per GPU, the per-GCD volume of the 48^3x96 production run on
  `--mpi 3.6.4.4`. One node, so the halos move by NVLink peer copies, not the network.
- Times come from nsys at boost clocks. Bytes, occupancy and stalls come from Nsight Compute
  (ncu replays at base clock with flushed caches, so its own times run long).
- Correctness: every run passed the benchmark's comparison against the Cshift reference
  (norm diff 2e-31 in fp64).

## Where one fp64 Dw goes (nsys, steady state)

| µs | stream 14 (compute) | elsewhere |
|---|---|---|
| 20–143 | 4 halo gathers | host waits for them |
| 143–228 | **idle** | host posts the sends |
| 228–984 | **interior Dslash, 756 µs** | 4 peer copies, 21 MB, one after another (380 µs) |
| 985–1058 | 4 merges | |
| 1058–1211 | exterior Dslash, 152 µs | |

On one node the halo copies hide under the interior kernel. Across nodes they go over MPI,
and do not hide (63% of the time with MPI in flight, in Peter's 288-GCD trace).

## Why the interior kernel is slow (ncu)

| | fp64 | fp32 |
|---|---|---|
| registers per thread | 104 | 69 |
| warps per SM allowed by registers | 16 | 28 |
| occupancy, achieved | 24% | 40% |
| warps ready to issue, per cycle | 0.13 | 0.57 |
| issue-active | 10% | 32% |
| DRAM traffic | 695 MB (59% of peak) | 214 MB |
| L2 hit rate | 64% | 77% |
| main stall | long_scoreboard (waiting on loads) | long_scoreboard |

- **Latency, not bandwidth.** DRAM has spare capacity, and the loads are coalesced (9.7
  sectors per request). There are too few warps in flight to cover load latency.
- **Block size cannot fix it.** `--accelerator-threads` changes the block size, but registers
  set the limit. A flat `--accelerator-threads` sweep is therefore what this model predicts;
  it does not show the kernel is bandwidth-bound.
- **fp64 also loses cache reuse.** fp32 moves 0.31x the bytes of fp64, not 0.5x, and its L2
  hit rate rises. fp64 moves 1.8x its 382 MB minimum: the neighbour spinors do not stay in
  the 40 MB L2.

## Experiments (one node, two repetitions each, agreeing to 0.3%)

| variant | Dw, full comms | change | Dw, sloppy comms |
|---|---|---|---|
| baseline (generic kernel) | 1172 µs | | 1237 µs |
| `--dslash-unroll` (separate run) | 1118 µs | −5% | |
| interior first, gathers on a second stream | 1095 µs | **−6.6%** | 1095 µs (−11.5%) |
| interior first + `--dslash-unroll` | 1037 µs | **−11.5%** | 1067 µs (−13.8%) |
| registers capped at 80 | 1337 µs | +14% | 1402 µs |
| registers capped at 64 | 2392 µs | **+104%** | 2456 µs |
| fp32 (`Benchmark_dwf_fp32`, separate run) | 505 µs | −57% (2.33x) | |

**Register caps make it worse.** At 64 registers occupancy doubles to 49%, but the kernel
spills 7.4 M times and moves 2.3 GB; at 80 it spills 2.8 M times. The registers hold real
data: each thread accumulates a full output spinor (12 complex, about 48 registers in fp64)
plus a half-spinor and link elements. More warps would need less work per thread (for
example spin or colour split across threads), not a compiler flag.

**Interior first saves less than estimated (6.6%, not ~17%).** The interior kernel now starts
at once and all gathers and copies hide under it. But it runs 862 µs instead of 756, because
the gathers and peer copies share its memory system. 208 µs off the critical path, minus
106 µs of slowdown, gives the measured 77 µs. The interior kernel is now the entire critical
path, so the next gain has to come from the kernel itself. The change should matter more
across nodes, where communication is longer.

## What to do next

1. **The interior kernel's register footprint.** Restructure so a thread holds less, for
   example splitting the spin or colour of one site across threads. That is the lever with
   the largest payoff (up to ~25% from the counters). Code-level work, best discussed with Peter.
2. **Interior first across nodes.** Test the stream change on 2+ nodes, where the halo goes
   over the network and Peter's trace shows 63% communication.
3. **fp64 cache blocking** for L2 reuse (fp64 traffic is 1.8x its minimum). A hypothesis.
4. **The same counters on MI250X** (rocprof-compute) once Frontier access arrives. The
   register file and wavefront size differ, so the A100 limit may not carry over.

## Limits

One node and `Benchmark_dwf`, not the multigrid smoother at 36 nodes. A100, not MI250X.
Random gauge field (performance does not depend on it). Savings marked "up to" are estimates
from counters; the experiment table is measured.
