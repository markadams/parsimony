2 / 8 · Why storage bits matter on the coarse grid

The coarse operator apply is bandwidth-bound at production batch

Per coarse site and stencil leg: a nbasis × nbasis complex block times nbasis × nrhs. In fp32 complex storage the arithmetic intensity is

AI = n·r / (n + 2r) flop/B

Below the roofline ridge, time is set by bytes of the stencil, and Grid's own measurement agrees: 530 → 728 GB/s as the batch grows on MI250X. After batching, the next lever is the width of the stored stencil.

Stencil bytes per coarse site at nbasis 62, 81 legs: 2.5 MB fp32, 5.0 MB fp64. 16-bit storage would halve the stream again.

3 / 8 · The tool

Parsimony: how few bits does each variable actually need?

Precimonious (SC'13) and its Blame Analysis follow-on (ICSE'16) came out of the Berkeley/LBNL CORVETTE project. They searched precision configurations by delta debugging and got the method right. The hardware was the problem.

Blame Analysis reported 0.0% speedup at every error threshold for half of its ten benchmarks. On a 2013 CPU, fp64 → fp32 bought nothing once the inserted casts were paid for.

bf16, fp8, tensor cores and bandwidth-bound kernels change the objective function, so the search algorithms are worth reviving. Parsimony is a clean-room reimplementation: no code from the 2013 tools, and the formats that matter now rather than the fp32/fp64/fp80 lattice of that era.

Two pluggable axes, so a cheap search and an expensive confirmation share one interface

AxisWhat plugs in
evaluatornumpy emulation for algorithms under design; a native binary taking formats on its command line, so no probe costs a rebuild; hardware timing
searchsolo-sensitivity prefilter for per-variable floors, then PrecisionDDMin delta debugging down the ladder
criterionrelative error, or convergence within an iteration budget

That third row is the design result, not a setting. For an iterative method, relative error against an fp64 run measures bit-reproduction of a rounding trajectory rather than solution quality, and for a preconditioner it measures nothing at all — a worse preconditioner changes the iteration count and cannot change the fixed point. Accuracy is held by the solver's own stopping test; precision trades against iterations.

Measured example: in a Bratu Newton–Krylov solve the stored Jacobian's knee is 10 ± 1 bits, and below it the solver never diverges. The nonlinear term falls under the ulp of the Laplacian's diagonal, Newton degenerates to Picard, and fp8 turns out to be slow rather than fatal.

Storage precision only: what is stored and re-read, not what is computed in a register3
4 / 8 · The study

Round each preconditioner input in storage, keep fp64 arithmetic, count outer iterations

Parsimony's method: a variable is stored at a virtual width of k significand bits (round-to-nearest, full exponent range), everything is computed in fp64, and a configuration passes if the outer HDCG solve converges within the reference iteration count, judged by an independent fp64 true residual of the fine operator.

Search: solo-sensitivity prefilter per variable, then delta-debugging over the ladder v53 v40 v30 v24 v16 v11 v8. Roughly 40–80 solves.

Result: a bit-knee per variable. That is the number an fp32-versus-fp64 comparison cannot give.

VariableRounded whereExpectation to test
subspacenear-null vectors after orthogonalisation, before coarseningGalerkin stays consistent; gentle degradation
stencilcoarse stencil blocks via GetMatrix / SetMatrixbreaks operator–projector consistency; may show a sharp knee
eveccoarse deflation eigenvectors before importonly the initial guess is affected; most tolerant

Not measured: reduced arithmetic (ComplexF coarse space, 16-bit compute types). This complements Peter's comparison rather than repeating it.

What the two columns say

Iterations never move. Five at every format, to eight bits. The coarse operator is rate-limiting, not accuracy-limiting: rounding it changes which problem is solved, not how long that takes. In HDCG it lives inside a preconditioner, where the fine operator fixes the answer — so this is the column that bears on 16-bit stencil storage, and it is flat.

The accuracy floor is the stored precision. δ ≈ 2−(k+1.2) across nine rungs over six decades, and the true residual follows it once it clears the solver tolerance. As a solve target the stencil needs ~30 bits at tolerance 1e−8 — which is log₂(1/tol) plus margin, not a property of the operator.

fp16 fails on exponent range, not precision. δ = 1 exactly: every entry underflows the 5-bit exponent and the stencil rounds to zero. bf16, with three fewer significand bits but fp32's exponent, is fine. These entries are unusually small in the free field, so the size of that effect is partly an artifact — the mechanism is not.

Emulation checked against hardware on real data: fp32 reproduces v24 and bf16 reproduces v8 to every digit.

7 / 8 · PETSc side

The same question for PETSc's blocked GPU operators

On the 1.05M-DOF elasticity beam, fp32 operator storage costs zero CG iterations, and the payoff is set by the format: on an A100, blocked fp32 SpMV runs 1.75× over blocked fp64 and 2.86× over scalar fp64. Scalar CSR cannot halve its time; its 4-byte index per nonzero caps the saving at 1.5×.

PETSc cannot express "fp64 outer solve, fp32 preconditioner" today without a whole-library single-precision build. The fork adds it in three steps, each gated on the frozen convergence result (19 CG iterations, tip displacement 1.23166).

StepWhatExit
Astored-value type separated from the vector type in every device kernel (MatScalar, ValT templates)bitwise-identical results
Bper-matrix fp32 shadow of the values, selected per objectgate holds hierarchy-wide in fp32; fp32 vector loads measured on both backends
Creduced-precision view installed as each level's smoother operator; residuals and outer Krylov stay fp64gate holds; end-to-end solve speedup on 1 and 8 GPUs

Multi-RHS smoothing (batched Chebyshev, point-block Jacobi) is the prerequisite for any PETSc component to sit inside an mrhs solve.

Questions for Peter

Written to be read rather than presented, so each one carries its own context. Q1 is the one that blocks the study. Pipeline, code and measured data, interactively: Parsimony on Grid.

Blocking

  1. Which driver should an HDCG precision study start from? tests/debug/Test_general_coarse_hdcg.cc needs MultiGeneralCoarsenedMatrix(geom, CoarseMrhs) followed by CoarsenOperator. That class now lives in Grid/algorithms/multigrid/deprecated/, and the block that used it in Test_general_coarse.cc is inside #if 0. On develop 865c338d, CUDA/sm_80, it segfaults inside the constructor — immediately after NonLocalStencilGeometry has 81 terms — at 1, 2, 4 and 8 ranks, with unit / hot gauge, Chebyshev or random subspace, nbasis 20 or 40, and --device-mem from 2 GB to 32 GB. Is that path expected to work, or should this move to MultiGeneralCoarsenedOperatorV2 / HDCGMultiGrid.h? If the latter, is there a driver to copy, or is writing one the first job?
  2. What do you run Test_general_coarse_hdcg on? The stock configuration (Ls 16, nbasis 40, 4⁴ blocks, 16³×32) does not fit four A100s: Test_general_coarse.cc at 1 rank dies with cudaMalloc failed for 8153726976 out of memory. Node count and any flags beyond systems/Perlmutter/config-command would save guessing.
  3. Where is ckpoint_lat.4000 on Perlmutter? A path is enough. Everything below is free-field, which is why it is preliminary.

About the measurement

  1. Does the flat iteration count match what you would expect of a physics coarse space? Rounding the coarse Dirac stencil in storage to as few as 8 significand bits left CG at 5 iterations, unchanged, while the attainable residual tracked 2−k exactly. Read as: the coarse operator is rate-limiting, not accuracy-limiting, so inside a preconditioner its stored width should be nearly free. Free field and a random subspace, so the conditioning is benign — does it survive a real ensemble?
  2. Is 16-bit storage of the coarse stencil worth doing? This is storage only — fp64 arithmetic throughout — so it is orthogonal to the 16F/BF16 compute types in GridBLAS. The apply is bandwidth-bound at production batch (AI ≈ 8.7 flop/B at nbasis 62, nrhs 12), so halving the stencil stream again is the next lever after batching. Is that interesting to Grid, or is fp32-vs-fp64 the only distinction that matters in practice?
  3. bf16 rather than fp16, if so. In our test fp16 destroyed the stencil outright (relative change 1.0 — every entry underflowed the 5-bit exponent) while bf16, with three fewer significand bits but fp32's exponent range, was indistinguishable from an 8-bit virtual format. Our entries are unusually small because of the free field, so the magnitude of that is partly an artifact — but do the coarse stencil entries in production sit comfortably inside fp16's exponent range, or is bf16 the only sane 16-bit choice?
  4. Which HDCG inputs would you predict to be most and least tolerant? The plan measures three — the near-null subspace, the coarse stencil, and the deflation eigenvectors. A prediction recorded before the measurement is worth more than one after it.

PETSc side

  1. Which Grid commit should PETSc pin, and with what configure flags? config/BuildSystem/config/packages/grid.py pins da593796 (March 2024): no multigrid/ directory, and the only flag passed is --enable-comms=mpi-auto, so it is a CPU-only GEN SIMD build. For anyone wanting a performance build through PETSc, what should the SIMD target, accelerator and shm settings be?
  2. Is a portable reference shell worth having alongside a Grid-backed one? On the PETSc side the lattice operators could be a parallel-correct, Hermitian-transpose-aware DMPlex shell used as the portable reference, with a second shell calling Grid directly in Grid's own layout. Useful, or duplicated effort?

Two patches, if wanted upstream

  1. Grid/perfmon/PerfCount.h — build break on current NERSC defaults. Under GRID_CUDA Grid defines no-op __rdtsc / __rdpmc shims to keep x86intrin.h away from nvcc, but cudatoolkit 13.2's header chain declares the real __rdtsc first: cannot overload functions distinguished by return type alone (unsigned long long vs uint64_t). Both uses are in Stat.cc, host-side, never in a device kernel, so replacing the shims with #include <x86intrin.h> fixes it and restores real timings.
  2. AdefMrhs.h — TwoLevelCGmrhs prints its iteration count but does not expose it. Added IterationsToComplete, TrueResidual and ConvergedFlag, filled on both exits, exactly as ConjugateGradient already does. Without it any automated study has to scrape stdout.
